> 16자리 이상 숫자 타입 응답값을 사용하면서 발생한 트러블슈팅에 대한 글입니다.

**이런 분께 추천합니다**

- JS 숫자가 왜 "정확하지 않을 수도 있는지" 궁금한 분
- `Number.MAX_SAFE_INTEGER`, `BigInt`를 이름만 들어본 분
- "정밀도 손실"이라는 말이 실제로 어떤 버그로 이어지는지 사례로 보고 싶은 분

## 1. 문제 상황

> 아래 예시는 실제 겪은 트러블슈팅 상황과 같은 원리를 보여주기 위해, 비슷한 형태의 값으로 각색한 예시입니다.

쇼핑몰 상품 목록에서 상품을 클릭하면, 그 상품의 `productId`로 상세 페이지를 요청합니다. 아주 흔한 패턴입니다.

서버 응답은 이렇습니다.

```json
{ "productId": 1234567890123456789, "name": "무선 이어폰" }
```

코드는 이 값을 그대로 옮겨 담기만 합니다.

```typescript
const selected = data.find((p) => p.id === clickedId);
router.push(`/products/detail?productId=${selected.productId}`);
```

**퀴즈: `console.log(selected.productId)`를 찍으면 뭐가 나올까요?**

정답은 `1234567890123456789`가 아닙니다.

```typescript
console.log(selected.productId);
// 1234567890123456800   ← 뒤 4자리가 바뀌었습니다
```

## 2. 원인을 좁혀나간 과정

1. 코드를 다시 봤지만 값을 가공하는 로직은 없었습니다 → **로직 버그 아님**
2. 네트워크 탭의 응답 원문과, 응답값을 사용한 `console.log` 출력값 · API 요청 쿼리 값을 나란히 비교했습니다.


| 위치             | 값                     |
| -------------- | --------------------- |
| 네트워크 탭 (서버 응답) | `1234567890123456789` |
| 콘솔 · API 요청 쿼리 | `1234567890123456800` |


두 값이 이미 다릅니다 → **응답을 받는 순간 자체에서 값이 깨진다**는 뜻입니다.

## 4. 근본 원인 — IEEE 754 double

### JSON은 잘못이 없습니다

JSON에서 숫자는 그냥 텍스트입니다. 몇 자리든 제한이 없습니다. 문제가 없는 구간은 **서버 → 네트워크 텍스트**까지입니다.

문제는 그 텍스트를 **JS 값으로 바꾸는 순간**입니다. JS는 숫자 타입이 `Number` 딱 하나뿐이고, 이 `Number`가 바로 IEEE 754 double(부동소수점 방식의 숫자 표현)입니다. 

### double은 "칸이 정해진 양식"입니다

double은 숫자 하나를 담을 때 항상 정확히 64비트를 씁니다.

가수부 52칸은 절대 안 늘어납니다. 값을 표현하는 데 필요한 유효비트 수가 53비트(가수 52비트 + 암묵적 선행비트 1)를 넘으면, **초과된 비트는 그냥 버려지는 게 아니라 가장 가까운 표현 가능한 값으로 반올림됩니다.** 정확히 중간(버려지는 부분이 딱 0.5 ULP)이면 마지막 남는 비트가 짝수(0)가 되도록 처리합니다.


|             | 10       | 2⁵³+1 (9007199254740993)            |
| ----------- | -------- | ----------------------------------- |
| 2진수         | 1010     | 100...0001 (54자리)                   |
| 53비트에 들어가나? | 예, 여유 있음 | **아니오, 1자리 초과**                        |
| 저장 결과       | 10 (정확)  | 9007199254740992 (더 가까운 짝수 쪽으로 반올림) |


`Number.MAX_SAFE_INTEGER`가 딱 2⁵³ − 1인 이유가 이것입니다. 

##### 안전한 정수 범위 

```js
Number.MIN_SAFE_INTEGER // -9007199254740991
Number.MAX_SAFE_INTEGER //  9007199254740991
```

### 왜 하필 JS만 이런가


| 언어     | 정수를 담는 방식                        |
| ------ | -------------------------------- |
| Python | `int` — 자릿수 제한 사실상 없음            |
| Java   | `long` / `BigInteger` — 정수 전용 타입 |
| **JS** | **`Number` 하나뿐 (double)**       |


JS는 1995년 열흘 만에 만들어지며 숫자 타입을 하나로 통일했습니다. 그 대가로 정수도 double의 한계를 그대로 물려받았습니다.

## 5. 검토했던 대안들

원인이 `JSON.parse` 시점의 double 변환이라는 걸 확인한 뒤, 실제로 이 문제를 고치기 위해 아래 방법들을 하나씩 검토했습니다.


| 방법                              | 핵심                                     | 결론                               |
| ------------------------------- | -------------------------------------- | -------------------------------- |
| `JSON.parse` reviver            | 값이 **이미 깨진 뒤**에 개입                     | 파싱 이후 개입하는 훅이라 소용없음              |
| axios `transformResponse`       | 원문 텍스트 단계에서 정규식 치환                     | 가능하지만 전역 파싱 로직을 바꿔야 함            |
| `json-bigint` / `lossless-json` | 표준 파서 자체를 교체                           | 새 의존성 추가 필요                      |
| `BigInt`                        | 정밀도 보존 가능한 타입                          | `JSON.parse`가 기본 지원 안 함 (하위 호환성) |
| source text access              | reviver가 원본 텍스트를 볼 수 있음 | V8엔 있음, 사파리·파이어폭스 아직 미지원         |


## 6. 실제 해결 방법 — 서버에서 string으로

프론트에서 파싱 방식을 바꾸는 대안들 대신, **서버에서 `productId`를 `string`으로 내려주기**로 정리했습니다. 
이유는 두 가지입니다.

- **복구 불가능**: `productId`는 계산이 아니라 식별용 값입니다. 정밀도가 한 번 깨지면 어떤 코드로도 원래 값을 되살릴 수 없습니다.
- **영향 범위가 작음**: 필드 하나 문제인데, 프론트 전역 파싱 전략을 바꾸는 건 비용 대비 손해입니다.

## 7. 실전 팁 — 큰 숫자·소수점을 안전하게 다루는 법

이번 트러블슈팅은 `productId` 하나였지만, 프론트엔드에서 자릿수가 긴 큰 숫자나 소수점을 다룰 일은 이 사례 말고도 많습니다. 앞으로 비슷한 값을 다룰 때 참고할 수 있게 정리해봤습니다.

- 금액 계산은 정수 최소단위(원이 아닌 전 단위 등)로 환산해서 처리합니다. (`0.1 + 0.2 !== 0.3` 회피)
- `toFixed()`는 숫자를 “반올림한 숫자”로 만들어주는 함수가 아니라, 숫자를 “문자열 형태로 포맷팅”하는 함수입니다. 계산 로직과 분리하세요.
- 정수 연산 전에 `Number.isSafeInteger()`로 안전 정수 범위인지 확인하는 습관을 들이세요.
- 식별용 큰 숫자(ID, 해시)는 애초에 API 설계 단계부터 `number`가 아니라 `string`으로 정합니다.
- 정밀 계산이 꼭 필요하면 `decimal.js`, `big.js` 같은 라이브러리를 씁니다.

## 8. 배운 점

*예전에 책에서 JS 숫자가 2진수로 저장되는 방식을 읽은 적이 있습니다. 그땐 "그렇구나" 하고 넘어갔습니다 — 그렇게 많은 자리의 숫자를 다루어 본 적이 별로 없어 와닿지 않았습니다.*

이번엔 달랐습니다. 직접 버그를 쫓아 원인을 파고드니, 해당 방식이 **실제 장애의 원인**이 될 수 있다는 걸 체감했습니다.
언어 설계 자체 단계까지 파고들어 근본 원인을 알아본 경험 덕분에, 앞으로 큰 숫자를 다룰 땐 무엇을 조심해야할 지 보다 분명하게 이해하고 오래 기억할 것 같습니다.
